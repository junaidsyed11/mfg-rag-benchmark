1. Project Overview & Goals

This project is a from-scratch RAG (Retrieval-Augmented Generation) system built specifically around aerospace manufacturing documents. The goal is to demonstrate — with working code and measurable benchmarks — that Cohere's embedding and reranking models produce better retrieval quality than alternatives for technical, domain-specific text.

The system was built in 12 steps, 10 of which are complete:

StepWhatStatus
1Generate 500 synthetic manufacturing documents with Llama 70BDone
2Token-aware sentence-boundary chunking (512 tokens / 64 overlap)Done
3Embed chunks with Cohere Embed v3Done
4Embed chunks with Cohere Embed v4Done
5Store vectors in ChromaDB (one collection per model)Done
6Dense retrieval (cosine similarity via ChromaDB)Done
7Sparse retrieval (BM25Okapi)Done
8Reciprocal Rank Fusion — merge dense + sparseDone
9Cohere Rerank v4 cross-encoder re-scoringDone
10Claude generation (via OpenRouter) — grounded answer from top-5 chunksDone
11Evaluation harness (MRR, NDCG@5, Faithfulness)Next
12README, cleanup, final polishNext

Why manufacturing documents?

General-purpose RAG benchmarks (MS-MARCO, Natural Questions) are saturated. Manufacturing quality documents — NCRs, ECRs, corrective actions — contain dense technical jargon, part numbers, supplier names, and traceability chains that stress-test retrieval in ways Wikipedia or news articles never will. This is where a specialist model like Cohere's should shine over general-purpose alternatives.

Why this is a Cohere portfolio piece

The entire retrieval chain uses Cohere: Embed v3 vs v4 as the benchmark comparison, and Rerank v4 as the final re-scoring step. The benchmark will produce concrete MRR and NDCG@5 numbers showing which model wins — something a Cohere Solutions Engineer can point to in a customer conversation.

3. Git Workflow

Why Git at all?

Git gives you a complete history of every change. If a refactor breaks something, git diff shows exactly what changed. For a portfolio project, the commit history itself is evidence of how the system was built — reviewers can see the progression from "empty repo" to "working pipeline."

Initial setup

git init                          # Create a new repo in the current directory
git remote add origin <url>      # Link to GitHub
git branch -M main                # Rename default branch to "main"

.gitignore — keeping secrets and large files out

The .gitignore file tells Git to completely ignore certain files. The most critical entries:

.env                  # API keys — if this leaks, attackers can burn your quota
.venv/                # Virtual environment — hundreds of MB, always recreatable
data/synthetic/       # LLM-generated data — reproducible, not source code
data/chunks/          # Derived from synthetic data — same reason
data/raw/             # Large CSVs
chroma_db/            # Vector database files — rebuilt by build_index.py
__pycache__/          # Python bytecode cache — not source
*.pyc
What happened during this project An API key was accidentally pasted into a terminal session that was being shared. The fix: immediately revoke the key on the provider dashboard, generate a new one, and update .env. A key in .env that is gitignored is safe — a key that appears in terminal output, commit history, or code is not.

Normal commit workflow

git status                        # See what files changed
git diff                          # See exact line-by-line changes
git add src/rag/generator.py      # Stage a specific file (safer than git add .)
git add scripts/query.py
git commit -m "feat: generator uses OpenRouter instead of Anthropic SDK"
git push origin main              # Push to GitHub

Why git add <file> instead of git add .? — git add . stages everything untracked, which can accidentally include .env if it was somehow missed by .gitignore, or large data files. Staging files explicitly forces you to think about what you're committing.

git stash — saving work-in-progress without committing

This was needed when config.yaml had a local change (switching to cohere-v3) but the remote had a different version. git pull refused to run because it would overwrite the local change.

git stash           # Temporarily shelves all uncommitted changes
git pull            # Now safe to pull — working tree is clean
git stash drop      # Discard the stash (we didn't need the local change back)
# OR:
git stash pop       # Re-apply the stashed changes after the pull

Think of git stash as a clipboard: it lifts your changes off the working tree, lets you do something (like pull), and then puts them back.

git pull — getting changes from GitHub

git pull origin main    # Fetch + merge remote changes into local branch

Under the hood this is two commands: git fetch (download remote commits) + git merge (apply them). If the merge is clean (no conflicts), it's automatic. If there are conflicts, Git marks the conflicting lines and you resolve them manually.

4. Virtual Environment & Package Management

What is a virtual environment?

Python has one global installation on your machine. If you install packages globally, every project shares them — version conflicts become inevitable. A virtual environment is an isolated copy of Python with its own site-packages/ folder. Packages installed inside it don't affect anything outside it.

python3 -m venv .venv          # Create the venv in a folder called .venv
source .venv/bin/activate      # Activate it (macOS/Linux)
# On Windows: .venv\Scripts\activate

# Your prompt now shows (.venv) — all pip commands go into this venv
which python                   # → /path/to/project/.venv/bin/python

pip install -e ".[dev]" — editable install

This is the most important install command in the project. Breaking it down:

PartMeaning
pip installInstall a package
-eEditable mode — install as a live link to src/ instead of copying files
.The package to install is defined by pyproject.toml in the current directory
[dev]Also install the optional dev extras (ruff, ipykernel)

Why editable? Without -e, pip copies your source files into site-packages/. If you edit src/rag/generator.py, Python still imports the old copy. With -e, Python imports directly from src/, so edits are reflected immediately without reinstalling.

# pyproject.toml defines the package:
[tool.hatch.build.targets.wheel]

# After pip install -e ., this just works everywhere in the venv:
from rag.generator import ClaudeGenerator

pyproject.toml — the modern package spec

Replaces the older setup.py / requirements.txt combo. It declares:

  • Project metadata: name, version, Python version requirement
  • Core dependencies: what the package needs to run
  • Optional groups: [dev] extras for development tools
  • Build system: hatchling (modern, fast, zero-config)
  • Tool config: ruff linter rules, pytest test paths

  final_top_k: 5                # Final results handed to Claude

Why these chunk parameters?

ParameterValueReasoning
chunk_size512 tokensDense models are trained at this context length. Longer = more context per chunk but worse precision. Shorter = more precise but may split important sentences.
chunk_overlap64 tokens~12% overlap prevents important information from being cut across chunk boundaries. A sentence at the end of chunk N also appears at the start of chunk N+1.
top_k20Cast a wide net at retrieval — we'll narrow it down with reranking. Getting the right document at rank 15 is fine if reranking surfaces it to rank 1.
rrf_k60The original RRF paper's recommended constant. Empirically generalises well without dataset-specific tuning.
final_top_k5LLM context has practical limits. 5 chunks of 512 tokens = ~2,500 tokens of context — enough for a detailed answer without overwhelming the model.

Why YAML over other formats?

Python (INI files) is too limited. JSON doesn't support comments. TOML works but is less readable for deeply nested configs. YAML supports comments, nested structures, and is human-editable — the right tradeoff for a config that researchers need to read and tweak.

How the generator works

The script builds a context dict for each document (random part numbers, suppliers, defect types from curated vocabulary lists), converts it into a detailed prompt, sends it to Llama 70B via OpenRouter, and writes the result as JSONL.

# call_llm() — sends the prompt to Llama 70B via OpenRouter
def call_llm(prompt: str, cfg: dict, api_key: str) -> str:
    sampling = cfg["synthetic"]["sampling"]
    response = requests.post(
        "https://openrouter.ai/api/v1/chat/completions",
        headers={"Authorization": f"Bearer {api_key}"},
        json={
            "model": cfg["synthetic"]["model"],  # meta-llama/llama-3.3-70b-instruct
            "messages": [{"role": "user", "content": prompt}],
            "temperature": sampling["temperature"],   # 0.8 — enough variety
            "top_p": sampling["top_p"],               # 0.92 — keeps domain vocab
            "frequency_penalty": sampling["frequency_penalty"], # 0.4 — avoid repetition
            "max_tokens": sampling["max_tokens"],   # 800 — full narrative
        },
        timeout=60,
    )
    response.raise_for_status()
    return response.json()["choices"][0]["message"]["content"].strip()

Sampling parameters explained

ParameterValueEffect
temperature0.8Controls randomness. 0 = deterministic (same output every time). 1.0 = very random. 0.8 hits the sweet spot — varied narrative while staying coherent.
top_p0.92"Nucleus sampling" — the model only considers the top 92% of probability mass at each token step. Prevents rare, off-domain words from appearing.
frequency_penalty0.4Penalises tokens that have already appeared. Prevents the model from repeating the same phrases across 500 documents.
max_tokens800Cap on output length. 800 tokens ≈ 600 English words — enough for a complete narrative without runaway generation.

  • Hand-written docs — impractical at 500-document scale for one person.

7. Step 2 — Token-Aware Chunking

Before a document can be embedded, it must be split into chunks. Embedding models have a context window (typically 512 tokens for retrieval models). A document that's 2,000 tokens long can't be embedded as a single unit — the model either truncates or errors. Chunking is the solution.

Why sentence-boundary chunking?

The naive approach is to split every N characters. But that can cut a sentence in half: "Porosity was detected on part PN-48" / "21-A during X-ray inspection." The embedding of the first half is semantically incomplete. Our chunker splits on sentence boundaries and only starts a new chunk when adding the next sentence would exceed 512 tokens.

Why tiktoken for token counting?

Cohere's tokenizer isn't public. Tiktoken's cl100k_base (used by GPT-4) counts tokens within a few percent of Cohere's for English technical text. The small discrepancy is acceptable — we're guarding against chunks that are wildly too long, not optimising to the exact token.

import tiktoken
_ENC = tiktoken.get_encoding("cl100k_base")

def _token_len(text: str) -> int:
    return len(_ENC.encode(text))
# encode() converts a string to a list of integer token IDs
# len() of that list is the token count

def _split_sentences(text: str) -> list[str]:
    # Split on . ! ? followed by whitespace
    # (?<=[.!?]) is a "lookbehind" — matches the position AFTER punctuation
    # \s+ matches the whitespace that separates sentences
    parts = re.split(r"(?<=[.!?])\s+", text.strip())
    return [p for p in parts if p]
def chunk_text(self, text: str) -> list[str]:
    sentences = _split_sentences(text)
    if not sentences:
        return []

    chunks: list[str] = []
    current: list[str] = []    # sentences accumulating in the current chunk
    current_tokens = 0

    for sentence in sentences:
        s_tokens = _token_len(sentence)

        # Edge case: one sentence alone exceeds chunk_size
        # Can't split further (no sub-sentence boundaries), so include it as-is
        if s_tokens > self.chunk_size:
            if current:
                chunks.append(" ".join(current))
            chunks.append(sentence)
            current = []
            current_tokens = 0
            continue

        # Adding this sentence would overflow the chunk — save current, start new
        if current_tokens + s_tokens > self.chunk_size and current:
            chunks.append(" ".join(current))

            # Build the overlap: walk backwards through current sentences
            # and collect sentences until we've accumulated chunk_overlap tokens
            overlap: list[str] = []
            overlap_tokens = 0
            for prev in reversed(current):
                pt = _token_len(prev)
                if overlap_tokens + pt > self.chunk_overlap:
                    break            # Adding this sentence would exceed the overlap budget
                overlap.insert(0, prev)   # Prepend to maintain order
                overlap_tokens += pt

            current = overlap             # New chunk starts with the overlap sentences
            current_tokens = overlap_tokens

        current.append(sentence)
        current_tokens += s_tokens

    if current:
        chunks.append(" ".join(current))   # Flush the last chunk

    return chunks

Visual walkthrough of overlap

Sentences S9 and S10 appear in both Chunk 1 and Chunk 2. This means a query that references something spanning that boundary will find relevant context in at least one of the chunks.

Alternatives

  • Fixed character splitting — simple but cuts sentences mid-word.
  • LangChain RecursiveCharacterTextSplitter — popular library approach, similar logic. We rolled our own to avoid adding a heavy dependency and to have full visibility into the algorithm.
  • Semantic chunking — embed every sentence, split when embedding distance between adjacent sentences exceeds a threshold. Better quality but 10-100× slower and requires an embedder at chunk time.
  • Paragraph-based splitting — split on double newlines. Simple but chunk sizes are unpredictable.

8. Steps 3 & 4 — Cohere Embeddings

What is an embedding?

An embedding converts text into a fixed-length vector of floating-point numbers (e.g., 1,024 or 4,096 dimensions). Similar texts produce vectors that are close together in high-dimensional space. "Porosity defect on turbine blade" and "X-ray revealed internal voids in stage-2 blade" will have vectors closer to each other than to "quarterly budget review."

Why Cohere? Why compare v3 vs v4?

Cohere Embed is purpose-built for retrieval. v4 introduced multi-modal input and improved performance on technical/domain-specific text. The benchmark will measure whether v4's improvements are meaningful for manufacturing QA documents — that's the story this project tells a Cohere customer.

The input_type distinction — critical detail

Cohere requires you to declare whether you're embedding a document (being stored) or a query (being searched). The model uses different internal encoding paths for each. Using the wrong type silently degrades retrieval quality — you'd get plausible-looking but sub-optimal results with no error message.

# config.yaml
input_type:
  document: "search_document"   # chunks at index time
  query: "search_query"         # user query at search time

CohereEmbedder — full implementation

class CohereEmbedder:
    def __init__(self, model, input_type_doc, input_type_query, api_key):
        self.co = cohere.ClientV2(api_key)   # Official Cohere Python client
        self.model = model
        self.input_type_doc = input_type_doc
        self.input_type_query = input_type_query

    def _embed_batch(self, batch: list[str], input_type: str):
        # Retry loop handles 429 Too Many Requests (trial key limit)
        while True:
            try:
                response = self.co.embed(
                    texts=batch,
                    model=self.model,
                    input_type=input_type,
                    embedding_types=["float"],  # Request float32 vectors
                )
                return list(response.embeddings.float_)
            except TooManyRequestsError:
                # Trial keys: 100 API calls/minute. Wait 61s, then retry.
                print(f"\n  Rate limit — waiting {_RETRY_WAIT}s ...")
                time.sleep(_RETRY_WAIT)

    def _embed(self, texts: list[str], input_type: str):
        all_vectors = []
        # Cohere API max: 96 texts per request
        for i in range(0, len(texts), _BATCH_SIZE):
            batch = texts[i : i + _BATCH_SIZE]
            all_vectors.extend(self._embed_batch(batch, input_type))
        return all_vectors

    def embed_documents(self, texts):
        return self._embed(texts, self.input_type_doc)  # "search_document"

    def embed_query(self, text):
        return self._embed([text], self.input_type_query)[0]  # "search_query"

The rate limit problem and fix

Cohere trial keys allow ~100 API calls per minute. With 350 chunks at BATCH_SIZE=96, we make ~4 API calls. That's well within limits for a single run. But when we ran v4 after v3 (two consecutive full index builds), we hit the limit at chunk 288. The fix:

  • Catch TooManyRequestsError in _embed_batch()
  • Sleep 61 seconds (one full minute + 1 second buffer)
  • Retry the exact same batch — it will succeed
v4 trial key issue embed-english-v4.0 requires a Cohere production key. Trial keys return a NotFoundError with a misleading message. The solution: add a production key to .env, or switch config.yaml to backend: "cohere-v3" for development. Both v3 and v4 collections can exist in ChromaDB simultaneously — switching backend changes which collection is queried.

9. Step 5 — ChromaDB Vector Index

What is ChromaDB?

ChromaDB is an open-source vector database. It stores (vector, document, metadata) triples and supports fast approximate nearest-neighbour (ANN) search. "Persistent" means vectors survive between Python sessions — you embed once and query forever.

class VectorIndex:
    def __init__(self, collection_name: str, db_path: Path):
        # PersistentClient writes to disk at db_path (default: ./chroma_db/)
        self.client = chromadb.PersistentClient(path=str(db_path))

        # get_or_create: idempotent — safe to call even if collection exists
        # hnsw:space: cosine distance metric (better for embeddings than L2)
        self.collection = self.client.get_or_create_collection(
            name=collection_name,
            metadata={"hnsw:space": "cosine"},
        )

Why cosine similarity?

Cosine similarity measures the angle between two vectors, not their magnitude. Two chunks that talk about the same topic produce vectors pointing in the same direction, regardless of how many words they contain. Euclidean (L2) distance punishes short chunks because their vectors have smaller magnitudes — cosine is invariant to this.

Collection naming

def _collection_name(backend: str) -> str:
    return f"mfg_rag_{backend.replace('-', '_')}"

# "cohere-v4"  →  "mfg_rag_cohere_v4"
# "cohere-v3"  →  "mfg_rag_cohere_v3"

Both v3 and v4 embeddings live in the same ChromaDB on disk, in separate collections. Switching config.yaml backend changes which collection is used — no file management needed.

The empty metadata bug

def _safe_metadata(meta: dict) -> dict | None:
    # ChromaDB rejects empty dicts {} as metadata — raises ValueError
    # Also rejects non-scalar types (lists, nested dicts)
    clean = {k: v for k, v in meta.items() if isinstance(v, (str, int, float, bool))}
    return clean if clean else None  # None is accepted; {} is not

Some chunks (from ASRS data) had metadata fields with list values or empty dicts. ChromaDB raises a ValueError on these. The fix strips non-scalar values and returns None for the entire metadata if nothing scalar remains.

Distance → Similarity conversion

# ChromaDB returns cosine DISTANCE: 0 = identical, 2 = opposite
# We want SIMILARITY: 1 = identical, -1 = opposite
# Conversion:
score = 1.0 - hit["distance"]

# Why? cosine_distance = 1 - cosine_similarity
# So cosine_similarity = 1 - cosine_distance
# This makes "higher = better" consistent across dense and sparse results

10. Steps 6 & 7 — Hybrid Retrieval

Why hybrid (dense + sparse)?

Dense retrieval (embeddings) excels at semantic similarity: "porosity" and "internal voids" are recognised as related even though they share no words. Sparse retrieval (BM25) excels at exact keyword matching: "NCR-2025-08324" or a specific part number will score highly only in BM25 — an embedding model may not preserve rare identifiers. Combining both gives the best of both worlds.

Dense retrieval implementation

def retrieve_dense(self, query: str, top_k: int = 20):
    # Step 1: embed the query with input_type="search_query"
    query_vec = self.embedder.embed_query(query)

    # Step 2: ask ChromaDB for the top_k most similar vectors
    raw = self.index.query(query_vec, top_k=top_k)

    # Step 3: convert distance to similarity
    results = []
    for hit in raw:
        results.append({
            "id": hit["id"],
            "document": hit["document"],
            "metadata": hit["metadata"],
            "score": 1.0 - hit["distance"],
        })
    return results

Sparse (BM25) retrieval implementation

# At construction time: tokenise every chunk and build the BM25 index
corpus = [c["text"].lower().split() for c in chunks]
self.bm25 = BM25Okapi(corpus)
# BM25Okapi uses Okapi BM25 — the standard probabilistic ranking function
# It considers term frequency (TF), inverse document frequency (IDF),
# and document length normalisation

def retrieve_sparse(self, query: str, top_k: int = 20):
    tokens = query.lower().split()       # Same tokenisation as the corpus
    scores = self.bm25.get_scores(tokens) # Returns array of float scores, one per chunk

    # argsort() gives indices that would sort the array ascending
    # [::-1] reverses it (now descending) and [:top_k] takes the top
    top_indices = scores.argsort()[::-1][:top_k]

    results = []
    for idx in top_indices:
        if scores[idx] <= 0:
            continue   # BM25 score of 0 means no query terms appear in the chunk
        chunk = self.chunks[idx]
        results.append({
            "id": _chunk_id(chunk),
            "document": chunk["text"],
            "metadata": {k: v for k, v in chunk.items() if k != "text"},
            "score": float(scores[idx]),
        })
    return results

BM25 — how it actually scores

BM25 (Best Match 25) scores a document d for query q as:

  score(d, q) = Σ IDF(qᵢ) · [ f(qᵢ,d) · (k1+1) / (f(qᵢ,d) + k1·(1-b+b·|d|/avgdl)) ]
  • IDF(qᵢ): Inverse Document Frequency — rare terms score higher than common ones
  • f(qᵢ,d): Term frequency in document d
  • |d| / avgdl: Length normalisation — prevents long documents from winning just by size
  • k1, b: Tuning constants. BM25Okapi uses k1=1.5, b=0.75 by default

11. Step 8 — Reciprocal Rank Fusion

After dense and sparse retrieval each return 20 results, we have two ranked lists that may overlap partially. RRF merges them into a single ranked list in a way that rewards documents appearing in both lists.

The formula

  RRF_score(d) = Σ  1 / (k + rank(d, list))
                lists

Where k = 60 (from the original Cormack, Clarke & Buettcher SIGIR 2009 paper) and rank is 1-based. A document at rank 1 in dense contributes 1/(60+1) ≈ 0.0164. A document at rank 20 contributes 1/(60+20) = 0.0125. A document that appears at rank 5 in both lists contributes 2 × 1/(60+5) ≈ 0.0308 — higher than any single-list document.

def reciprocal_rank_fusion(result_lists, k=60):
    scores: dict[str, float] = {}
    docs: dict[str, dict] = {}

    for result_list in result_lists:
        # enumerate with start=1 gives 1-based rank
        for rank, hit in enumerate(result_list, start=1):
            doc_id = hit["id"]
            # Accumulate: same doc_id in multiple lists adds up
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
            # Keep the first-seen copy of each document's data
            if doc_id not in docs:
                docs[doc_id] = hit

    # Sort by accumulated RRF score, descending
    ranked = sorted(scores.items(), key=lambda x: x[1], reverse=True)
    return [{**docs[doc_id], "rrf_score": score} for doc_id, score in ranked]

Why k=60 specifically?

Lower k (e.g. k=10) amplifies the gap between rank 1 and rank 2 — giving top-ranked results a much larger score boost. Higher k (e.g. k=100) flattens the curve — rank 1 and rank 20 get more similar scores. k=60 was empirically shown in the original paper to generalise well across retrieval tasks without tuning per dataset. It's become the de-facto default.

Alternatives to RRF

  • Score normalisation + addition: Normalise both score lists to [0,1] then add. Problem: BM25 scores and cosine similarities have very different distributions — normalisation is sensitive to outliers.
  • Learned fusion (LambdaMART): Train a ranker that learns how to combine signals. More powerful but requires labelled training data we don't have.
  • CombMNZ: Another classic fusion method. Multiply the sum of scores by the number of lists the document appears in. Similar effect to RRF but sensitive to score scale.

12. Step 9 — Cohere Rerank

What is a reranker?

A bi-encoder (like Cohere Embed) encodes each document independently and finds nearby vectors. This is fast but coarse — the query and document never interact during encoding. A cross-encoder reads the query and one document together and produces a joint relevance score. It's far more accurate but too slow to run on the full corpus (500+ documents). The reranker runs only on the top-20 fused candidates.

def rerank(self, query: str, candidates, top_n=None):
    if not candidates:
        return []   # Skip API call entirely for empty input

    n = top_n if top_n is not None else self.default_top_n
    n = min(n, len(candidates))   # Can't return more than we have

    response = self.co.rerank(
        model=self.model,         # "rerank-v4.0-fast"
        query=query,
        documents=[c["document"] for c in candidates],
        top_n=n,
    )

    # response.results is sorted by relevance_score descending
    # r.index is the position of this result in our candidates list
    return [
        {**candidates[r.index], "rerank_score": r.relevance_score}
        for r in response.results
    ]

Model name correction

The original config had rerank-english-v4.0 (wrong). The Cohere API returned a NotFoundError. The correct model name is rerank-v4.0-fast. This was identified by checking the Cohere docs / API model list.

Alternatives to Cohere Rerank

  • FlashRank: Open-source cross-encoder, runs locally. No API cost but lower quality and requires GPU for speed.
  • BGE Reranker (HuggingFace): Strong open-source alternative. Works well for general text but not specifically tuned for retrieval.
  • ColBERT: Late interaction model — stores token-level embeddings and scores at query time. More accurate than bi-encoders, cheaper than full cross-encoders.
  • No reranker: Just use the RRF-fused top-5. Simpler but lower precision — worth benchmarking as a baseline.

13. Step 10 — Claude Generation via OpenRouter

What is RAG generation?

The retriever finds the most relevant chunks. The generator reads those chunks as context and produces a grounded natural-language answer. The key constraint: Claude must answer only from the provided context — no external knowledge. This makes the answer verifiable and the system honest about what it knows.

Why OpenRouter instead of the Anthropic SDK directly?

OpenRouter is an API gateway that provides access to models from many providers (Anthropic, Google, Meta, Mistral, etc.) under a single API key. The project already had an OpenRouter key for Llama 70B (synthetic generation). Reusing it for Claude avoided adding a second API key and separate billing account.

_OPENROUTER_URL = "https://openrouter.ai/api/v1/chat/completions"

# System prompt — defines the assistant's constraints
_SYSTEM_PROMPT = """\
You are a quality engineering assistant for an aerospace manufacturing company.
Answer the user's question using ONLY the information in the provided context documents.
If the answer cannot be found in the context, say so clearly — do not guess.
When referencing specific information, cite the document ID (e.g. "per NCR-2024-00042").
Be concise and precise. Use technical language appropriate for a quality engineer.\
"""
def _format_context(chunks):
    parts = []
    for i, chunk in enumerate(chunks, start=1):
        doc_id = chunk.get("doc_id", "unknown")
        doc_type = chunk.get("doc_type", "")
        supplier = chunk.get("supplier", "")

        # "[1] NCR-2025-08324 (NCR · Apex Precision Components):"
        header = f"[{i}] {doc_id}"
        if doc_type:
            header += f" ({doc_type}"
            if supplier:
                header += f" · {supplier}"
            header += ")"
        parts.append(f"{header}:\n{chunk['document']}")
    return "\n\n".join(parts)  # Double newline separates chunks visually

def generate(self, query: str, chunks):
    if not chunks:
        return "No relevant documents found for this query."

    context = _format_context(chunks)
    user_message = f"CONTEXT:\n{context}\n\nQUESTION: {query}"

    response = requests.post(
        _OPENROUTER_URL,
        headers={
            "Authorization": f"Bearer {self._api_key}",
            "Content-Type": "application/json",
        },
        json={
            "model": self.model,       # "anthropic/claude-sonnet-4-6"
            "messages": [
                {"role": "system", "content": _SYSTEM_PROMPT},
                {"role": "user", "content": user_message},
            ],
            "max_tokens": self.max_tokens,  # 1024
        },
        timeout=60,
    )
    response.raise_for_status()  # Raises HTTPError for 4xx/5xx responses
    return response.json()["choices"][0]["message"]["content"].strip()

The display bug fix

After generation was working, the chunk display in query.py showed ? (?) for doc_id and doc_type. The reason: ChromaDB stores metadata in a nested metadata dict, but the display code looked for doc_id at the top level of the result dict (where it doesn't exist after reranking).

# Before (broken):
doc_id = r.get("doc_id", "?")           # Always "?" — not at top level

# After (fixed):
meta = r.get("metadata") or {}          # Nested metadata dict
doc_id = r.get("doc_id") or meta.get("doc_id", "?")
doc_type = r.get("doc_type") or meta.get("doc_type", "?")
